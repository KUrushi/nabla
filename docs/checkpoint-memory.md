# チェックポイントのピークメモリと世代管理（issue #244）

`save-checkpoint` / `load-checkpoint` が大きなファイルでどれだけメモリを使うかを測り、葉ごとの遅延読み込みと世代管理（最新 n 個を残す）が要るかを判断した記録。

## 結論

- **ピークは、読み込みでファイルの約 2 倍、保存で約 3 倍（木の分を含む）**。SBCL の既定の `dynamic-space-size`（1 GiB）では、読み込みは約 450 MiB（448 MiB は通り、512 MiB は枯渇）、保存は約 290 MiB（256 MiB は通り、320 MiB は枯渇）のチェックポイントまでしか扱えない。
- **フェーズ5には葉ごとの遅延読み込みは要らない**。フェーズ5の状態（データパイプラインの位置・PRNG キー・小さな配列）は KB 級で、フェーズ4のモデルも MB 級。実装はしない。大きなモデル（目安: パラメータ + Adam の状態が 300 MiB を超える、つまり約 25M パラメータ以上）を扱う段階で、別の Issue にする（§4）。
- **世代管理は要らない**。保存はアトミックなので、最新の 1 個は常に壊れない。「最新 n 個を残す」は学習ループの方針（フェーズ5以降）で、呼び出し側が数行で書ける（§5）。
- データパイプラインの状態は、**Lisp の整数ではなく配列で持つ**。`defmodule` の `:state` スロットに入れれば、モデル + オプティマイザ状態と同じ木で往復する（§3）。

## 1. 測定環境

| 項目 | 値 |
| --- | --- |
| OS / CPU | macOS（Darwin 27.0.0）、arm64、メモリ 16 GiB |
| 処理系 | SBCL 2.6.7 |
| `dynamic-space-size` | 既定の 1 GiB（`sb-ext:dynamic-space-size` = 1073741824）と、8 GiB を指定した場合 |
| 対象 | f32 のテンソルだけの木（リスト）。`few` = 同じ大きさの葉 4 枚、`mixed` = 大きな葉 4 枚（全体の 3/4）+ 小さな葉 4096 枚（残り 1/4） |
| 合計の大きさ | 64 / 256 / 1024 MiB |

再現: `scripts/measure-checkpoint-memory.sh`（ケースごとに別の SBCL プロセス。`scripts/measure-checkpoint-memory.lisp` が 1 ケースを測る）。

測り方:

- 指標は **最大 RSS**（`getrusage` の `ru_maxrss`）。`dynamic-usage` を GC のたびに拾う方法（スクリプトの `:heap-peak-mb`）は、GC の間の山を逃すので参考値にとどめる。
- 「倍率」は **ピーク RSS ÷ ファイルの大きさ**。save では木そのもの（値が 0 の f32 配列）を含み、load はひな形を `aval` にして木の分を持たない。基準の RSS（木を作って full GC した直後）は約 60 MiB で、256 MiB 以上では無視できる。
- `ru_maxrss` はプロセスの一生の最大で、nabla/nn をロードする山が約 300 MiB あるので、**64 MiB のケースの RSS は読めない**（`dynamic-space-size` が 1 GiB のときは山が小さく読める）。倍率は 256 MiB 以上で見る。

## 2. 結果

最大 RSS（MiB）。かっこ内はファイルの大きさに対する倍率。

| 操作 | 構成 | 合計 | `dynamic-space-size` 1 GiB | 8 GiB |
| --- | --- | ---: | ---: | ---: |
| load | few | 256 | 571（2.2x） | 575（2.2x） |
| load | mixed | 256 | 601（2.3x） | 603（2.4x） |
| load | few | 1024 | **ヒープ枯渇** | 2111（2.1x） |
| load | mixed | 1024 | **ヒープ枯渇** | 2274（2.2x） |
| save | few | 256 | 827（3.2x） | 831（3.2x） |
| save | mixed | 256 | 936（3.7x） | 879（3.4x） |
| save | few | 1024 | **ヒープ枯渇（SBCL が落ちる）** | 3135（3.1x） |
| save | mixed | 1024 | **ヒープ枯渇（SBCL が落ちる）** | 3427（3.3x） |

（1 GiB のヒープ枯渇は、load では `storage-condition` で捕まえられた。save は GC の最中に枯渇して SBCL が終了した。64 MiB は 1 GiB のヒープで load 187 / 194、save 251 / 275 MiB で通る。）

上限を絞るために 1 GiB のヒープで 320 / 384 / 448 / 512 MiB（few）も測った。load は 448 MiB（ピーク 954）まで通り 512 で枯渇、save は 256 MiB（827）が通り 320 MiB から枯渇した。

読み取り:

- **load は約 2 倍**。`read-safetensors` がファイル全体を 1 本の octet 配列に読み（1 倍）、葉ごとに配列へコピーする（もう 1 倍。結果として残る分）。octet 配列は読み終えたあとに捨てられるが、ピークでは両方が生きている。
- **save は約 3 倍**（木そのもの 1 倍 + 木から作る葉ごとの octet 列 1 倍 + 全体を 1 本にまとめた `encode-safetensors` の結果 1 倍）。木の分は呼び出し側が持っているものなので、保存が上乗せするのは約 2 倍。
- 小さな葉が 4096 枚あっても（`mixed`）倍率はほとんど変わらない。葉の数は支配的でない。
- 所要時間は 1 GiB で load 0.3〜0.5 秒、save 1〜1.4 秒（ディスクのキャッシュに載る範囲。メモリが主な制約で、時間ではない）。

## 3. データパイプラインの状態

フェーズ5のデータパイプライン（Grain 相当）の状態は、**配列だけの `defmodule`** にして、モデルとオプティマイザの状態と同じ木に入れる。

```lisp
(defmodule pipeline-state ((epoch :state)        ; rank 0 の :i32 配列
                           (position :state)     ; バッチ内の位置。rank 0 の :i32 配列
                           (shuffle-key :state)  ; (prng-key seed) か split の1行。:u32 の (2)
                           (buffer :state)))     ; 小さな配列
(save-checkpoint path (list model opt-state pipeline))   ; "2.epoch" "2.shuffle-key" ...
```

- **Lisp の整数・実数を葉にすると `:bad-leaf`**（保存でもひな形でも）。これは意図した挙動で、変えない。理由: 葉は必ず dtype を持つ配列で、`tree-unflatten` で復元したときに型が決まるため。オプティマイザの `count`（rank 0 の `:i32` の配列。Lisp の整数にすると `jit` が毎ステップ再コンパイルする）と同じ方針で、**状態は配列で持つ**。
- PRNG のキーは `prng-key` が作る `:u32` の `(2)` の配列で、そのまま葉になる（`split` の結果の 1 行も同じ形）。往復したキーから `split` した結果はビット単位で元のキーと同じ。
- 文字列で足りる補助情報（データセットのパスや版など）は、`save-checkpoint` の `metadata` に入れてもよい。ただし配列の状態をメタデータに書き込むと形・dtype の照合が効かなくなるので、状態は葉にする。
- テスト: `tests/nn/checkpoint-test.lisp` の `checkpoint/pipeline-state-in-the-train-state-tree-round-trips`（medium。モデル + オプティマイザ状態 + パイプラインの状態の木を PBT で往復し、整数の端（i32 の最小・最大）、符号付き・符号なしのシードから作ったキー、キーの `split` までビット単位で確かめる）と `checkpoint/lisp-integers-are-not-leaves`（Lisp の整数は `:bad-leaf`）。
- この issue でコードは変えていない（上のテストは今の挙動を固定する）。パイプラインの状態をどういう構造にするかはフェーズ5の最初の Issue で決める。

## 4. 葉ごとの遅延読み込みは要るか

**フェーズ5には要らない**。

- フェーズ5で保存する状態は、パイプラインの位置・キー・小さなバッファで KB 級。モデルは `examples/transformer.lisp` の規模（MB 級）。どちらも 1 GiB の既定のヒープで余裕がある。
- 既定のヒープで通る上限（目安）: load は約 450 MiB、save は約 290 MiB（32〜64 MiB 刻みで測った。葉の構成で多少動く）。パラメータ + Adam の 2 つの状態（f32 で 3 倍）に直すと、約 25M パラメータ（save が先に限界）。GPT-2 small（124M パラメータ、f32 で約 500 MiB、Adam の状態を含めて 1.5 GiB）は、1 GiB の既定では保存も読み込みもできず、8 GiB のヒープでも save のピークは約 4.5 GiB になる。
- 回避策はある: `--dynamic-space-size` を上げる。nabla が追加で用意するものではなく、利用者が SBCL の起動オプションで指定する。

**別の Issue にする条件**: 25M パラメータを超えるモデルを扱う段階（フェーズ6以降の想定）。そのときの方針の候補（実装はしない。オーケストレータが Issue 化を判断する）:

1. **読み込み**: ヘッダだけ先に読み、テンソルごとに `read-sequence` で配列の記憶域へ直接読む（ファイル全体の octet 配列をやめる）。ピークは 2 倍から約 1 倍 + 最大の葉に下がる。ファイル形式は変えない。`load-checkpoint` に「必要な葉だけ読む」形（ひな形の葉だけ）を足すと、パイプラインの状態だけを先に読むことも、モデルだけ読むこともできる。
2. **保存**: `encode-safetensors` で全体を 1 本にまとめず、ヘッダを書いてから葉を 1 つずつ書く（ピークは木の分 + 最大の葉の octet 列）。一時ファイル + rename のアトミックさは保てる。
3. テストの観点: 既存のバイト列の一致（`encode-safetensors` の出力と、Python の safetensors で書いたファイルの読み込み）が、ストリーム版でも保たれること。

## 5. 世代管理（最新 n 個を残す）は要るか

**要らない**（今は作らない）。

- 「保存の途中で落ちても前のチェックポイントを失わない」は、一時ファイル + rename（`write-safetensors`）で既に満たしている。世代管理が守るのは、それとは別の失敗（保存したチェックポイントそのものが学習の発散後に使えない、ディスクの破損、評価値が良かった時点に戻したい）。
- 「何世代残すか」「評価値で選ぶか」「いつ消すか」は学習ループの方針で、ライブラリの `save-checkpoint` に持たせると、`best` を残す・n 世代 + 最良 1 個を残す、のような要望ごとに引数が増える。呼び出し側が保存先のパス名にステップ数を含めて（`(format nil "ckpt-~8,'0D.safetensors" step)`）、保存後に古いものを消せば足りる（`uiop:directory-files` で数行）。
- フェーズ5の再開（データパイプラインの位置を含む）に必要なのは最新の 1 個だけ。学習ループ（フェーズ5より後）を作る段階で、必要になったら `save-checkpoint` の外の小さな関数として足す。
- 補足: `write-safetensors` は `finish-output` までで `fsync` を呼ばない。OS のクラッシュや停電に対しては、rename したファイルが空になりうる（プロセスが落ちるだけなら安全）。必要になったら世代管理とは別に直す。
