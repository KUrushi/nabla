# Mutation testing の手順と runner の仕様

mutation testing† は「テストがバグを見つけられるか」をテストする手法。コードに小さなバグ（変異体†）をわざと入れ、テストが落ちるか（変異体を殺せるか）を確かめる。落ちずに生き残った変異体は、テストの抜けを示している。

## 目次

1. 手順
2. 変異演算子
3. 対象と除外
4. 生き残った変異体への対処
5. runner（`tools/mutate/`）の仕様

## 1. 手順

1. 既定のテストスイートが通ることを確認する。落ちている状態で変異をかけても、結果に意味がない
2. PR で変更した行を対象に、runner を実行する
3. 生き残った変異体を1つずつ読み、「4. 生き残った変異体への対処」に従って対処する
4. 足した性質で変異体が殺せるようになったことを、runner を再実行して確かめる
5. 結果（変異体の数、殺した数、除外した数と理由）を PR の説明に書く

## 2. 変異演算子

| 名前 | 変更の例 | 見つけたいテストの抜け |
| --- | --- | --- |
| 算術演算子の入れ替え | `+`↔`-`、`*`↔`/` | 計算結果の値を確かめていない |
| 比較の境界 | `<`↔`<=`、`>`↔`>=` | 境界の値（0、形状の端）を試していない |
| 定数の置き換え | `n` → `0`、`1`、`(- n)` | 定数の意味（軸の番号、初期値）を確かめていない |
| 条件の反転 | `(if c a b)` → `(if (not c) a b)` | 分岐の両側を試していない |
| 分岐の入れ替え | `(if c a b)` → `(if c b a)` | 同上 |
| 式の削除 | `(progn a b c)` → `(progn a c)` | 副作用（キャッシュへの登録、解放）を確かめていない |
| 返り値のゼロ化 | ルール関数の返り値 → `0` またはゼロ配列 | jvp / transpose / バッチ化ルールの値を確かめていない |
| 軸の入れ替え | `transpose` や `moveaxis` の軸の並び → 別の並び | 形状が対称な入力でしか試していない |

1行に複数の変異がかけられるときは、Google の運用にならって1行につき1つだけ選ぶ。すべてを試すと時間がかかり、似た結果が並ぶだけになるため。

## 3. 対象と除外

対象:

- コア: IR、トレース、変換（jit / grad / vmap）、プリミティブのルール、StableHLO 出力、jit キャッシュのキー計算
- nn / data の純粋関数（レイヤーの計算、オプティマイザの更新式、サンプラー、トランスフォーム）

対象外:

- CFFI のバインディング（`nabla/iree`、`nabla/pjrt` の foreign 関数定義）。ポインタや構造体の変異はクラッシュを起こすだけで、テストの抜けについて何も教えてくれない
- テストコードそのもの

arid node†（変異させても意味のない箇所）として、次は変異させない。

- ログ出力、`format` による表示
- エラーメッセージやコンディションの文字列
- `declare`、`declaim`、`the` などの型宣言・最適化宣言
- docstring

## 4. 生き残った変異体への対処

生き残った変異体ごとに、次のどれかを行う。

1. **性質を足す**（第一の選択肢）: その変異体でだけ結果が変わる入力を考え、それを含むように性質か生成器を強くする。例: `<`↔`<=` が生き残ったら、境界の値を生成器が出すようにする
2. **等価変異体として除外する**: どんな入力でも振る舞いが変わらないと判断できたら、除外リストに理由つきで記録する
3. **コードを直す**: 変異させても振る舞いが変わらないのは、その式が不要だからかもしれない。不要なら消す

「テストを書くのが面倒だから除外する」はしない。除外するのは、振る舞いが変わらないと説明できる場合だけ。

除外リストは `tools/mutate/exclusions.lisp` に、次の形で書く。

```lisp
(:file "src/core/primitives/add.lisp"
 :form "(defprimitive add ...)"
 :mutation "(* 1 x) -> (/ x 1)"
 :reason "x に 1 をかけても割っても値が変わらない等価変異体")
```

## 5. runner（`tools/mutate/`）の仕様

実装済み。使い方の詳細は [`tools/mutate/README.md`](../../../../tools/mutate/README.md) を見る。

```sh
# main から HEAD までの git diff で変わった .lisp の行が対象（既定）
tools/mutate/run.sh

# ファイルや行範囲を指定する
tools/mutate/run.sh src/core/foo.lisp:10-40
```

- `run.sh` は既定で対象システム（`--system`、既定 `nabla`）の `<system>/tests`
  （既定 `nabla/tests`）を読み込んでからテストを実行する。#4（テスト基盤）が
  マージされる前や、対象システムの `/tests` が存在しない場合は
  `--test-system` と `--test-form` で明示的に指定すること
  （[`tools/mutate/README.md`](../../../../tools/mutate/README.md) 参照）
- 入力: 対象のファイルと行の範囲（既定は `git diff` で `main` から変わった行のうち、
  `src/` 以下の `.lisp`。`src/iree/` と `src/pjrt/` の CFFI バインディングは除く）
- ソースを Lisp の reader で読み、変更した行を含むトップレベルの定義（`defun`、`defmethod`、`defmacro`、`defprimitive`）を探す
- 各定義に変異演算子（算術演算子の入れ替え・比較の境界・定数の置き換え・`if` の分岐の入れ替え、この順）を1つずつ試し、最初に適用できたものを1つの変異体として、変異させた定義を image に `eval` してロードする
- 対象のシステムのテストスイートを実行し、落ちれば「殺された」、通れば「生き残った」とする。無限ループに備えてタイムアウトを設け、タイムアウトは「殺された」とみなす
- 変異体ごとに元の定義をロードし直してから次に進み、変異が他の変異体の結果に混ざらないようにする
- 出力: 変異体ごとの（ファイル、行、変更前後の式、結果）の一覧と、mutation score†（（殺した数＋タイムアウト数） ÷（全数 − 除外数））
- mutation testing 中は、PBT の試行回数を既定より減らしてよい（変異体の数だけスイートを繰り返すため）。ただし減らしすぎると殺せる変異体を見逃すので、生き残った変異体は既定の試行回数で再確認する（runner はこれを自動でやる）
